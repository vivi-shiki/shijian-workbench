# 古籍诗集结构化

以页面图像和多套 OCR 为证据，输出忠实、可校订的诗歌类古籍电子书结构。适用于诗集、词集、曲集、诗文合集，以及带笺注、评点的选本。OCR 只提供候选文字和位置，不代表正确阅读顺序或文体边界。

## 强制生产流程

本节约束 OCR 文本、作品边界、句读、注文和电子书结构的生成、纠错与重跑。Codex 的职责是改进生成系统，外部大模型负责生成内容候选，用户负责最终批准。纯方案讨论、仅修改 skill、UI 或运行环境修复不触发付费模型调用。

`用户反馈 -> 证据与失败分类 -> 修改代码中的规则和校验 -> 外部模型生成候选 -> 独立验收与回归 -> 用户批准 -> 应用及经验更新`

所有入口共用候选生命周期：`create -> inspect -> approve|abandon`。网页、CLI、MCP 或 Codex 不得直接把模型输出写入正式电子书；它们必须调用同一核心候选命令。自动校验只生成警示和 `issues`，不拒绝候选，也不替用户批准。真正阻止应用的条件仅包括候选哈希不匹配、正式基线已经变化、候选已处理或缺少明确批准说明。

- 必须先修改代码，再通过已配置且获准使用的外部大模型迭代。代码修改包括真正被调用的提示词模板、任务划分与上下文逻辑、校验器及回归用例；仅改本 skill、临时环境变量、反馈字符串或口头承诺不算完成代码修改。规则已存在时，应先增加能复现本次失败的回归用例并检查规则为何未生效，不为满足流程制造无关改动。
- 禁止默认由 Codex 直接改正式 `structured.json` 或 OCR 结果，禁止先手改答案再让外部模型复述，也禁止把答案硬编码到后处理脚本后宣称模型已修复。不得把用户原话原封不动作为修订指令转发；原话可以留作审计证据，调用时必须使用分析后的约束与相关事实。
- 默认最多三轮外部模型修订，通过即可提前停止。三轮仍未通过时保留原正式结果和候选，报告失败项并等待用户决定；不得自动转成人工兜底，也不得沿用过去任务的“三轮后自行修复”授权。本次用户明确要求制作标准答案或单次人工修复时，才可在指定范围内例外操作，并单独记录为人工或 Codex 修订，不计为模型能力改进。
- 外部服务不可用、未授权或缺少凭据时，先完成可离线验证的代码与回归用例，说明尚未运行；不得用 Codex 自产 JSON 冒充外部模型结果。遵守用户指定模型、页范围和预算，不擅自扩大重跑范围。

## 反馈迭代步骤

1. **冻结基线与取证。** 读取当前代码、正式 JSON、相关原页、全部选中的 OCR 结果和已有项目经验。保留基线版本或哈希；将用户明确提供的校正视为对应局部事实，不当作其他作品的答案。`AI_CONTEXT.md` 中的 AI 修改记录不是用户已批准经验。
2. **语义化反馈。** 持久化反馈记录，至少包含原话、失败类别、适用范围、证据页或区域、期望行为、可检查断言、未知项和批准状态。适用范围分为 `local`、`project`、`general`；`validation` 表示可机械检查的问题类型，`ambiguous` 表示证据不足。局部事实只进入案例，本书惯例只进入项目层，不把诗名、具体补句或个别特例升级为通用规则。
3. **先改系统代码。** 根据根因修改实际执行路径：模型不知道规则就改提示词，丢失相邻页就改任务分片与上下文，能机械检出的错误就改校验器。每条拟推广的通用规则至少绑定一个真实页面回归案例，新增规则保持 `proposed`，未经用户确认不得标记 `approved`。先跑离线测试；不能用删掉失败断言、放宽门槛或写死预期输出来获得通过。
4. **构造模型任务。** 从上述记录生成任务规格，提供规则、最小相关页面及前后重叠上下文、两套或多套 OCR 的独立来源、当前候选和验收要求。明确待处理页与只读上下文页，既保留跨页连续性又限制改动范围。人工给出的确切文字可以标记为人工证据，但不得预先由 Codex 拼好整份目标 JSON 交给模型抄写。
5. **生成独立候选。** 调用外部模型前检查脚本是否会覆盖正式结果；若只有直接覆盖模式，必须先实现候选模式，不能以“有备份”为由跳过。每轮保留实际请求、原始响应、解析后的候选、差异、验收结果和版本信息。记录 `prompt_version`、`skill_version`、`memory_revision`、代码版本或差异哈希、输入哈希、模型标识和运行 ID；版本必须对应实际内容，日志不得包含密钥。
6. **逐轮验收再改代码。** 校验器独立于生成过程，检查下节门槛及关联的已批准回归案例。失败项转化为下一轮的具体诊断，并先修改对应提示词、代码或回归用例，再调用外部模型；不得只重复相同提示词三次，也不得直接把用户原话当作下一轮反馈。未能验证的语义问题记为 `needs_review`，不因 JSON 可解析或模型自称正确就判为通过。
7. **批准后才应用。** 展示修改了哪些规则、每轮警示、候选差异及尚需用户判断的内容，明确正式结果尚未被替换。只有用户明确批准该候选及其适用范围后，才通过统一候选接口应用；应用前检查候选哈希和基线哈希，避免覆盖期间的人工修改。Agent 代用户执行时记录 `actor=ai:codex`、`channel=agent` 和授权来源，不伪装成人工界面操作。只把用户确实确认的事实或规则标为 `approved`，不能把整轮 AI 结果自动升级为经验。

反馈、候选和批准记录应通过项目已有存储与日志接口维护；缺少所需机制时先补实现，不另造一套绕过审计的临时写入流程。遵守仓库 `AGENTS.md` 的 begin/commit 协议；不手工编辑 `history/` 或 `ai-memory/`。记录必须区分外部模型生成、自动校验、Codex 复核、用户批准和最终应用。

## 候选验收门槛

- 结构合法、ID 唯一、页码与来源可追溯；模型不得修改任务范围之外的正文或既有人工校订。
- 仅句读排版任务去除标点与空白后字符序列必须一致；OCR 纠错或补漏任务的每处增删改字必须有页面、OCR 或人工证据，无法确认则保留疑问，不用格律猜补。
- 检查跨页续接、漏诗、重复条目、组诗序号和总数；体裁字数与句数是检查线索，不能单独替代作品边界判读。
- 分别检查注文文字保存、所属作品及精确锚点；offset 在范围内不等于语义位置正确。拆合注文应按内容覆盖和各自锚点验收，不要求机械保留旧数组分组。
- 对比基线与候选，运行本次案例及关联已批准案例；没有用户批准标准答案的案例只能标为待复核，不得自行宣布全量正确。数据校验、浏览器展示和文本语义分别报告；失败项写入警示，不丢弃候选。

## 判读顺序

1. 先按竖排从右到左、每栏从上到下恢复版面顺序，再判断文体。
2. 以清晰原图和人工修订为最高证据；多套 OCR 用于互证和补漏，不能当作两份正文。
3. 大字通常是正文或题名，贴在正文旁的双行小字通常是逐句注文。不要把字体大小不同但位置相邻的文字直接拼接。
4. 不翻译、不润色、不补写。可补现代标点，但保留繁体、异体、人名和原书用字。疑字进入 `issues`。

## 分类

- `heading`：卷名、年次、小目录和其他独立目录标题。`heading_level` 只表示抽象目录层级，使用数字 1-6，数字越小层级越高；通常卷名为 1、卷内年次为 2，但不得把“年份”等具体语义写死为某一层级。校订者可按原书结构自由调整层级。目录标题统辖到下一个同级或更高层级标题，不能写成某首诗的标题、副标题或组题。
- `book_text`：扉页题字、撰注者题署、出版题记等属于书籍、但不是作品或序跋的文字。放入 `lines`，按原版语义分行。
- `biography`：县志、墓志等作者传记。题名放 `title`，传文放 `prose`，不得误作诗题。
- `preface`：序、跋等散文。没有明确作者栏时保持 `author` 为空；文末落款保留在正文中，不据此臆造标题作者。
- `poem`：一篇独立韵文一个条目，可承载诗、词、曲、乐府、联句等；正文放 `lines`，体裁放 `form`，不得因字段名为 poem 就强判为近体诗。
- `note`、`colophon`、`other`：仅在前述类型均不适用时使用。

扫描机构后加的“数位化”“典藏”等水印不进入正文。版心、页码、书口、重复刊印信息也不作为作品内容；无法判断是否原书内容时记录问题，不直接删除。

## 组诗与注文

- 组诗总题不能消失。每首子诗仍是独立 `poem`，使用相同 `series.title`、递增的 `series.index`，总数明确时写 `series.total`。除非原书另有子题，各首 `title` 留空；前台依据数字 `series.index` 显示“其一、其二”等中文序次，不把序次写进题名。词曲的组作也采用同一关系，但不得把词牌或曲牌误作目录标题。
- 近体诗按每句字数、句数、偶数句押韵和版面题名共同判体：七绝为四个七言句，七律为八个七言句，五律为八个五言句。古体诗、乐府、词、曲和联句按原题、体式、分阕及版面边界处理，不强套绝句或律诗句数。不要把注文中的引诗误算成正文；也不把跨页残句硬凑成一首。
- `lines` 的每项只放一个完整诗句并带标点。前台再把相邻两句合成一个排版段落；不得为追求视觉上的“两句一行”而在 JSON 一项中粘入两句，更不得一项粘入四句。
- 竖排题名统辖其左侧后续正文，直到下一个同级题名。题名右侧的正文通常属于前一作品，这是拆分跨栏、跨页作品的重要边界。拆分时同时检查五七言字数、绝句或律诗句数、押韵和注文归属；不能只按 OCR 区块顺序决定边界。
- 题名较长时也要按完整句意添加现代标点，必要时为题名中的引诗加引号。题名旁的小字说明仍作为 `notes` 记录，并用 `{ "field": "title", "offset": n }` 定位，不得把说明文字揉进题名。
- 原版用连续空框、墨钉或明确留白表示阙文时，每缺一字记一个 `□`。可按五言、七言句式将连续缺字符号分配到各句，但不得据上下文猜补原字；在 `issues` 中说明阙文。
- 每条注文放在所注诗的 `notes` 中，使用 `position` 记录圈号应插入的精确位置，不保存引文式 `marker`。诗句位置写为 `{ "field": "lines", "line": 1, "offset": 7 }`，其中 `line` 从 1 开始，`offset` 是该行第几个 Unicode 字符之后；独立题下注写为 `{ "field": "title", "offset": 4 }`；组诗总题下注写为 `{ "field": "series", "offset": 4 }`。必须依据注文引文和原版小字位置确定所注的具体词语，把圈码放在该词语之后；不得机械挂到句末，同一句中锚点不同的注文也不得合并。`text` 只保存注文正文。每首诗结束后立即结束其注文归属，不把整组注文汇总到最后。
- `notes[].text` 应按完整句意添加现代中文标点，区分书名、人名、篇名、引诗和按语；引用关系明确时使用冒号，引文内部继续断句。不能只在注文末尾机械加句号，且除标点和空白外不得增删改任何原文字符。
- 注码显示遵循 CY/T 121-2015：正文使用真正的 Unicode 带圈数字 `①②③`，紧跟被注文文字并以上标显示；注文列表使用相同带圈数字，注码与正文一一对应。不要用 CSS 边框把普通阿拉伯数字伪装成圈码。
- 小字若实际是下一句正文，不得因 OCR 标成注释就放入 `notes`。用字号、栏位、句式和四句边界共同复核。

## 序跋句读与分段

- `preface`、`biography` 等文言散文应按完整句意添加现代中文标点，识别主谓、转折、承接、引语、书名、人名、年号和落款，不按固定字数机械断句。
- 按论旨转换、叙事阶段、评议、作序缘起和落款划分自然段；一个完整意思原则上保持在同一段，避免每句一段。JSON 的 `prose` 使用两个换行符分隔自然段。
- 句读和分段只能添加或调整标点与空白。去除标点和空白后，文字序列必须与输入完全一致，不得改字、繁简转换、补写或删节。

## 输出检查

- 书名、各级目录标题、组题、撰者和注者信息均有保留，`heading_level` 反映相对层级而非标题语义。
- 传记没有成为诗题，序文没有虚构作者。
- 每首绝句句数合理，跨页续接明确，组诗序号连续。
- 注文紧跟其所属单诗，没有混入诗句或跨首聚合。
- `source_pages` 可追溯，低置信文字和边界进入 `issues`，不以猜测填平。
